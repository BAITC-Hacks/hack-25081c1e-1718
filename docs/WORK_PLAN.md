# План на 300 минут — Дима и Азим

T0 — начало работы по объявленному кейсу. Окно команды 5 часов; в исходном guide указано 9 часов. План не меняет официальный дедлайн. При позднем подключении Азим ориентируется на текущую контрольную точку, а не начинает свои 300 минут заново.

Уточнение пользователя после kickoff: Дима сейчас работает один и публикует свою часть. Зоны Азима сохраняются. OpenAI переносится на этап 60–150 сразу после первого каркаса; это ограниченный советник с автономным fallback, без дополнительного сервера или GPU. Первый каркас опубликован в main: 1a025b4. Первые часы ниже считаются относительно общего T0, а не с момента присоединения второго участника.

## Правила переключения при отставании

- Нет G1 к 60-й минуте: оба решают совместимость/лимиты; приоры и UI откладываются.
- Нет G2 к 150-й: Дима сохраняет рабочую стратегию, Азим завершает один совместимый data-модуль; веб получает только просмотр отчёта.
- Нет G3 к 220-й: сдавать автономный режим при нестабильном API, убрать дополнительную полировку из критического пути, сосредоточиться на исправлении падений/лимитов и документации.
- После T+240 принимаются только исправления сдачи, воспроизводимости и демо. После T+290 — проверка наличия файлов/пуша.
- UI может работать с сохранённым успешным отчётом: обязательно указать seed, время и что это сохранённый прогон. Не выдавать фикстуру за расчёт.

## Коммиты и синхронизация

1. Перед сессией и зависимой интеграцией: `git pull --rebase --autostash`.
2. По уточнению пользователя каждый владелец коммитит связанный законченный кусок с проверками примерно каждые 4 активные минуты. Перед checkpoint: fetch, посмотреть входящие изменённые файлы и чужой STATUS/HANDOFF. Не коммитить ради таймера сломанный интерфейс; не менять входы текущего benchmark посреди его выполнения.
3. Указывать конкретные изменённые файлы при checkpoint. Общие manifests/контракты интегрирует Дима; чужие личные заметки не менять.
4. После пуша в свой HANDOFF: SHA, законченная функция, затронутый контракт, что подключить и следующий шаг. Изменение интерфейса также записать в DECISIONS.
5. Второй разработчик перед зависимой задачей делает pull и читает handoff. Это обмен через Git, а не автоматическая передача истории Codex-чата.
6. При конфликте сохранять обе реализации/намерения, не force-push и не сбрасывать чужую работу. Неочевидное решение описать в QUESTIONS и перейти на независимую задачу.
7. Состав итоговой отправки проверяет Дима. Азим подтверждает воспроизводимость отдельным запуском и записью своего SHA/команды/результата.

## Первый handoff Азиму — историческая запись

На момент первого handoff Дима завершил ядро и два этапа OpenAI, оставив данные и web/ Азиму. Оба реальных API-вызова работали; тогда экономическая устойчивость была неудовлетворительна (3/10 положительных). Следующие пункты описывают начальную передачу; data-этап уже выполнен, см. актуальный раздел выше.

1. Подтянуть main репозитория https://github.com/BAITC-Hacks/hack-25081c1e-1718; выполнить agent-sync, прочитать также docs/RUNBOOK.md и docs/BASELINE.md.
2. Создать candidate_model.py с **build_candidates(profile, tariffs, data_dir) -> list[dict]**. Сигнатура ровно из трёх аргументов; tariffs — DataFrame. Поля кандидата и ограничения фильтров — в ARCHITECTURE. Ядро подключает модуль автоматически.
3. Работать в candidate_model.py и analysis/: исследовать публичную историю, устойчиво сглаживать priors, учесть цену/пакеты/потребление, не делать ID join разных выборок. Не подбирать тарифы под скрытые mock-эффекты.
4. Запушить data-модуль с собственным LOG/HANDOFF/STATUS и описанием, что нужно подключить. Затем реализовать web/ по docs/DESIGN.md: импорт фактического report.json, кампании, пилоты, ресурсы, ограничения; форматы не менять. Данные брать из генератора, не придумывать.
5. Азим обновляет README и проверяет воспроизводимость своей части. Дима параллельно меняет agent.py, llm_advisor.py и scripts/; эти файлы, manifests и общий контракт Азим не редактирует без записи в QUESTIONS и согласования.
6. Каждая законченная часть — небольшой проверенный Conventional Commit и push через checkpoint с явным списком файлов. Перед интеграцией pull/rebase, сохранять обе стороны при конфликтах, не force-push. Ключи только в окружении; пакет организаторов не менять и скрытые исходники не исследовать.
